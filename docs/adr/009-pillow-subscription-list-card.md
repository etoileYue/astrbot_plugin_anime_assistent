# ADR-009：使用 Pillow 生成分页追番列表卡并缓存封面 URL

## 背景

`/sub list` 原本只返回纯文本。随着条目增多，标题、进度、收藏状态、连载状态和排期信息难以快速浏览。仓库已有图片卡技术调研，但插件部署在 AstrBot Docker 环境中，不适合为了一个固定列表布局引入 Chromium 或依赖外部截图 RPC。与此同时，每次查看列表都逐条查询 Bangumi 或重复解析图片会增加延迟和失败面。

## 决策

- 首版只使用 Pillow 生成 PNG，不引入 Playwright 或远程 RPC。
- 画布固定宽 1600px，按页眉 220px、每条 300px、页脚 80px 动态计算高度；每页最多 6 部，保持数据库 `created_at DESC` 顺序，多页图片放入同一个 AstrBot `chain_result`。
- `subscriptions.cover_url` 持久化 Bangumi `images` 中按 `large → common → medium` 选择的封面 URL，不保存图片二进制。添加订阅和收藏同步时写入非空 URL；上游没有封面时不覆盖旧缓存。
- 旧记录首次列出时以最多 4 个并发 Bangumi 请求补齐 URL。图片下载使用插件级共享异步 `httpx.AsyncClient`，只接受 HTTP/HTTPS，总超时 10 秒、单图上限 8 MiB、最多 6 个并发；图片解码和绘制在线程中执行。
- 缺失或下载失败的封面使用带标题首字的粉彩占位图。页面绘制失败后以全占位封面重试；字体不可用或重试仍失败时返回原有完整纯文本列表。
- 字体优先使用可选 `card_font_path`，其次使用随插件分发的 Apache-2.0 Droid CJK 字体和 DejaVu Sans，再寻找常见 Noto/Droid 系统字体；数字和拉丁字符按段回退。内置字体避免 AstrBot Docker 镜像缺少 CJK 字体时无条件降级，最终仍没有可用字体时记录明确原因。

## 原因

- 列表是固定、规则的二维布局，Pillow 足以完成并能提供跨环境相对稳定的结果。
- 不安装 Chromium、不调用公共 RPC，可降低镜像体积、启动成本、外部服务依赖和数据合规风险。
- URL 缓存能避免列表命令每次为所有条目请求 Bangumi，同时保留上游更新封面的能力；不缓存二进制可避免数据库膨胀和缓存失效管理。
- 6 条分页兼顾移动端查看高度、单图体积和平台消息限制。
- 完整纯文本降级保证字体、网络、损坏图片或 Pillow 异常都不会使核心列表不可用。

## 替代方案

- 使用 Playwright 截取 HTML/CSS：排版灵活，但需要 Chromium 运行时，资源占用和部署复杂度明显更高。
- 调用远程截图 RPC：本地负担低，但引入可用性、鉴权、隐私和服务维护依赖。
- 每次查看实时请求所有封面且不持久化 URL：实现简单，但延迟和 API 失败面随条目数线性增加。
- 把封面二进制存入 SQLite：减少重复下载，但显著放大数据库，并需要过期与刷新策略。
- 图片失败时只发送部分成功页面：会让用户误以为列表条目缺失，因此选择整组回退完整纯文本。

## 影响

- 新增运行依赖 `Pillow>=10.1.0` 和可选配置 `card_font_path`。
- 插件包增加约 4.6 MiB 的 Droid CJK 与 DejaVu Sans 字体资源，并随附各自许可证。
- `subscriptions` 增加可空 `cover_url`；初始化迁移可重复执行，兼容旧数据库。
- 插件生命周期新增共享图片客户端，卸载时必须关闭。
- `/sub list` 正常返回一到多张 Base64 PNG；空列表仍返回原提示，任一页面最终失败时返回原完整纯文本。
- 列表渲染、远程图片安全边界和纯文本格式化可以分别进行单元测试。
