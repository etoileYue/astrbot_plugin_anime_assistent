# ADR-010：按番剧合并活跃访谈范围

## 背景

用户可能先将同一番剧的第 17–18 集标为已看，收到访谈首问后尚未作答，又继续看完第 19–20 集。原实现按 `(subject_id, start_episode, end_episode)` 保存活跃会话，因此会创建两个同番剧访谈，要求用户用路由前缀区分回复，也会产生拆分的观感记录。

## 决策

活跃访谈按 `subject_id` 唯一管理。同一番剧出现更高观看进度时，将已有会话的终点扩展到最新集数，而不创建第二个会话。

- 首问尚未回答时，替换首问并发送覆盖完整范围的新问题。
- 已有回答时，保留全部问答和轮次，只提示范围已扩展；后续追问、评论上下文和 Markdown 记录使用新范围。
- 评论预取在扩展时取消并重新发起，避免遗漏新集数评论。
- 只更新当前内存会话写入的 `interviews` 记录，避免影响历史访谈。
- 消息路由保持“进度同步优先于访谈回答”，使用户可在访谈期间继续标记进度。

## 原因

- 同一部番剧连续观看的观感通常适合在一个上下文中讨论。
- 一个番剧一个活跃会话消除了不必要的同番剧路由前缀和重复首问。
- 保留已回答内容不会打断正在进行的访谈，也能让最终 Markdown 反映完整观看范围。

## 替代方案

- 保留多个会话并要求前缀路由：增加用户操作负担，不能满足连续进度合并的需求。
- 仅在首问未回答时合并：用户只要先回复一次就会重新遇到重复会话。
- 合并时丢弃旧访谈重新开始：会丢失用户已提供的观感内容。

## 影响

- `InterviewHandler` 的活跃会话索引改为 `subject_id → InterviewEngine`。
- 同一番剧的后续、重复或落后进度分别表现为扩展、无操作或保留当前会话。
- 不同番剧仍可同时活跃，仍使用现有路由前缀机制。
